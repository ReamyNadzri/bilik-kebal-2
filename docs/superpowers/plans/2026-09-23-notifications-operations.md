## Slice 1: private inbox foundation

Add an append-only migration, published notification contract, authenticated list
and mark-read APIs, and correlation IDs with allowlisted operational logging.
Notifications contain an event kind and opaque identifiers only. Render fixed
English messages; never accept arbitrary message bodies, file names, reviewer
notes, bank details, email addresses or URLs as notification payloads.

Acceptance criteria:

- A recipient can list only their own notifications, including when restricted.
- Anonymous users cannot access inbox data; staff have no inbox bypass.
- Clients cannot insert notifications or change content or ownership.
- Trusted event ingestion is idempotent by event ID and recipient. Reusing that
  key with different event data fails instead of silently rewriting history.
- Mark-read is recipient-scoped and preserves its first timestamp on retries.
- Pagination uses a stable descending `(created_at, id)` cursor.
- API responses are private/no-store, validate input, and expose safe errors.
- Logs contain only generated correlation ID, operation, outcome, duration and
  status; request bodies, user IDs and provider errors are excluded.
- Unit/API tests and SQL access-control tests cover these behaviors.

## Subsequent slices and dependencies

### Slice 2: recorded domain events (Owner: Codex)

Publish claim-review and account-restriction events through domain-owned database
triggers calling the notification enqueue contract in the same transaction.
Recipients come from the owning domain's row, never client input. Stable review
and restriction UUIDs prevent duplicate inbox delivery. Existing records are not
backfilled. Competing claims marked not-selected receive the winning review's
event UUID scoped by recipient and only when the owning review selects them.
To avoid collapsing multiple losing claims by one recipient into the same key,
not-selected fanout is deferred until a per-claim selection event contract exists.

Acceptance: approve/reject/request-information and new account restriction create
exactly one recipient notification; no-op/repeated restriction, metadata updates,
failed review, unauthorized operation and rolled-back transaction do not publish.
No notes, evidence, email, bank data or file names enter the inbox. Neither email
delivery nor settlement operations are triggered by this slice.
